# Creating an EF migration

`dotnet ef migrations add` scaffolds three `/// <inheritdoc />` comments into the migration file (one
on the class, one on `Up`, one on `Down`). This repo does not keep them — every migration `.cs` in
both projects has zero. Remove them as part of creating the migration, not as a separate cleanup.

## Steps

1. **Build first.** The migration tooling builds the project, and a stale `Api.exe` holding
   `bin\Debug\net10.0\Api.exe` will fail the build with `MSB3027`. If that happens, stop and tell the
   user which PID holds it rather than killing it.

2. **Add the migration.** Name it `{Verb}{What}To{Entity}` to match the existing files
   (`AddVoiceToConversationParticipant`, `AddNextSpeakerPositionToConversation`):

   ```powershell
   dotnet ef migrations add <Name> --project Backend/Api
   ```

   Use `--project Backend/Identity` for `ApplicationDbContext`. Note that Identity calls
   `EnsureCreatedAsync()` at startup rather than applying migrations, so an Identity migration will
   not reach an existing database on its own.

3. **Strip the comments** from the generated migration file — **not** the `.Designer.cs`, which is
   `// <auto-generated />` and keeps its comment:

   ```bash
   sed -i '/^\s*\/\/\/ <inheritdoc \/>$/d' Backend/Api/Migrations/<timestamp>_<Name>.cs
   ```

   The whole line goes, leaving no blank line behind. The result should read:

   ```csharp
   namespace Api.Migrations
   {
       public partial class AddNextSpeakerPositionToConversation : Migration
       {
           protected override void Up(MigrationBuilder migrationBuilder)
   ```

4. **Verify** with `grep -c inheritdoc` on the migration file — it must be 0.

5. **Apply it by hand.** Domain migrations are not applied at startup:

   ```powershell
   dotnet ef database update --project Backend/Api
   ```

## Checking existing migrations

To find any migration that still carries the scaffolded comments:

```bash
grep -lc inheritdoc Backend/*/Migrations/*.cs | grep -v Designer
```
